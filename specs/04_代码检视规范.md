# 代码检视规范

> 本文档为只读文档。
> Godot 4.x 代码检视（Code Review）规范。AI 在**阶段 9（质量门禁）**做 code review 及**阶段 8（开发自检）**时**必须**加载并遵循本规范。
> 与 `requesting-code-review` Skill（review 流程）协同，以前三份规范（`01_GDScript`/`02_场景`/`03_TDD`）为检查基准。
> 每条含：规范说明 + 正例（✅）+ 反例（❌）。

---

## 一、检视流程与态度

### 1. 早检视、常检视

**说明**：每完成一个 story/功能、合并前**必须** code review；越早 review，问题越不易堆积。

**正例**（✅）：完成 story S01-03 后立即 review，再进入下一个 story。

**反例**（❌）：攒一大堆功能最后才 review，问题交织、难定位、难回退。

### 2. 聚焦改动集（review diff）

**说明**：针对本次改动的 diff 检视；不在本次改动范围内的问题记录待办，不跑题挑老代码。

**正例**（✅）：`git diff BASE..HEAD` 只看本次新增/修改，聚焦相关逻辑。

**反例**（❌）：借 review 之机，要求作者「顺手」重构无关的旧模块——偏离本次目标、扩大风险。

### 3. 只读检视，不改代码

**说明**：检视者只读不写——用 `git diff`/`git show` 查看，不修改工作区/分支；如需在不同 revision 验证，用单独 worktree。

**正例**（✅）：只给反馈（file:line + 问题 + 修法），由作者修改。

**反例**（❌）：检视者直接动手改作者分支的代码——职责混乱、难以追责。

### 4. 先肯定优点，再提问题

**说明**：先具体指出做得好的地方（建立信任），再列问题；准确的肯定让作者更愿意接受后续反馈。

**正例**（✅）：`### Strengths\n- 测试覆盖完整（18 个用例含边界）\n- 信号解耦清晰` 再列 Issues。

**反例**（❌）：上来直接劈头盖脸列问题，毫无肯定——作者易产生防御心理。

### 5. 对事不对人

**说明**：评价**代码**不评价**人**；技术分歧用技术理由（代码/测试佐证）反驳，不带情绪。

**正例**（✅）：`这里每帧 load() 会卡顿，建议 preload 并缓存（见 01 规范第11条）。`

**反例**（❌）：`你这写法太差了` / `你怎么连这个都不懂`——人身攻击，无建设性。

## 二、反馈分级与表达

### 6. 按严重度分级

**说明**：问题分三级——**Critical**（bug/崩溃/数据丢失/安全）、**Important**（架构缺陷/功能缺失/错误处理不足/测试缺口）、**Minor**（风格/优化/文档）；不把吹毛求疵标成 Critical。

**正例**（✅）：
```
#### Critical
- player.gd:42 未判 is_instance_valid 直接调用，敌人销毁后崩溃
#### Important
- 缺少 take_damage 为负的边界测试
#### Minor
- MAX_SPEED 可抽为 @export 便于调参
```

**反例**（❌）：把「变量名不够优雅」标成 Critical，淹没真正严重的问题。

### 7. 反馈具体可操作

**说明**：每条反馈含 `file:line` + 问题是什么 + 为何重要 + 如何修（非显然时）。

**正例**（✅）：`enemy.gd:88 — _process 内每帧 instantiate 子弹，造成卡顿；建议用对象池（见 01 规范第16条）。`

**反例**（❌）：`性能不太好，优化一下` —— 无位置、无原因、无方向。

### 8. 给出明确结论

**说明**：检视结束给出明确裁定——**Ready**（可合并）/ **With fixes**（修完指定项即可）/ **No**（需重大返工），附 1-2 句技术理由。

**正例**（✅）：`Ready to merge: With fixes — 核心实现扎实，仅需修 Critical（空指针）与补边界测试。`

**反例**（❌）：`看起来还行吧` —— 无明确裁定，作者不知能否推进。

## 三、检查重点

### 9. 对照需求与验收标准

**说明**：首要检查——实现是否符合 story 的需求与 AC；合理偏离要标明，缺失功能要指出。

**正例**（✅）：逐条对照 AC，确认 `take_damage`、边界 clamp、死亡信号均实现并测到。

**反例**（❌）：只看代码「漂不漂亮」，不验证是否满足 AC——功能缺失却被漏过。

### 10. 逻辑与边界

**说明**：检查逻辑正确性，尤其边界（0/空/越界/负值）与异常路径。

**正例**（✅）：`hp.current = 10; hp.take_damage(20)` 是否 clamp 到 0 而非负数？

**反例**（❌）：只测 happy path（正常输入），忽略 `take_damage(-5)` 会加血这类逻辑漏洞。

### 11. 资源生命周期

**说明**：检查 Node/Resource 的创建与释放——`instantiate`/`new` 是否有对应 `free`/`queue_free`/`auto_free`，避免泄漏。

**正例**（✅）：测试中 `auto_free(Timer.new())`；场景节点用 `queue_free()` 清理。

**反例**（❌）：`var fx := hit_fx.instantiate(); add_child(fx)` 播完不释放——内存泄漏。

### 12. 信号耦合（Godot 重点）

**说明**：检查通信方向——子发信号父监听（signal up）、父调用子（call down）；禁止 `get_parent()` 链与兄弟节点直访。

**正例**（✅）：`Health` 发 `died` 信号，`Player` 监听后处理死亡。

**反例**（❌）：`weapon.gd` 内 `get_parent().get_parent().on_ammo_empty()` —— 脆弱且紧耦合。

### 13. 性能隐患（Godot _process 重点）

**说明**：检查 `_process`/`_physics_process` 内是否有每帧开销——`load()`、`instantiate`、全树搜索、轮询；应改用 preload/对象池/信号/缓存。

**正例**（✅）：`_ready` 里 preload 并缓存引用；状态变化用信号通知。

**反例**（❌）：`_process` 内 `if get_tree().root.find_child("Enemy"): ...` —— 每帧全树搜索。

### 14. 类型安全

**说明**：检查类型提示是否齐全（变量/参数/返回值/信号）；节点有效性用 `is_instance_valid` 而非 `!= null`。

**正例**（✅）：`func find_enemy(pos: Vector2) -> Enemy:` + `if is_instance_valid(target):`

**反例**（❌）：无类型注解 + `if target != null:`（已释放节点仍可能为 true）。

### 15. 测试充分性

**说明**：检查是否遵循 TDD 规范（`03`）——有无先行的失败测试、边界与错误路径是否覆盖、是否测公开行为而非内部实现。

**正例**（✅）：`test_zero_damage`、`test_overkill_clamps`、`test_negative_input` 均存在且通过。

**反例**（❌）：只有一个 happy path 测试，且是「先写实现后补」——无失败验证。

## 四、检视纪律

### 16. 以前三份规范为检查基准

**说明**：`01_GDScript`（24 条）、`02_场景`（19 条）、`03_TDD`（18 条）是检视的成文基准；发现违反即按对应规范条目指出。

**正例**（✅）：`违反 01 规范第6条——节点引用应用 @onready + 类型，而非 _ready 内 get_node。`

**反例**（❌）：凭主观喜好挑刺，不引用客观规范——反馈无标准、难服众。

### 17. 格式交给 lint，review 管逻辑

**说明**：代码风格（缩进/空格/换行）交给 `gdlint`/`gdformat` 自动处理；review 聚焦逻辑、架构、正确性、性能。

**正例**（✅）：review 关注「信号耦合是否合理」「边界是否覆盖」，而非「缩进 2 空格还是 4 空格」。

**反例**（❌）：把 review 时间花在格式细节上——那是 lint 的职责，浪费 review 带宽。

### 18. 不要求过度设计（YAGNI），接受合理偏离

**说明**：只要求当前测试/需求所需的功能（YAGNI）；实现相对计划的合理改进偏离应被认可，而非机械对照计划挑刺。

**正例**（✅）：`当前测试只需固定 3 次重试，不必提前抽 maxRetries 参数——YAGNI，通过。`

**反例**（❌）：`这里应该支持可配置的重试次数、退避策略、回调...`——测试未要求，过度设计。

## 附：检视输出模板与自查清单

**检视输出格式（参照 requesting-code-review Skill）：**

```
### Strengths
[具体指出做得好的地方]

### Issues
#### Critical（必须修）
[bug / 崩溃 / 数据丢失 / 安全]
#### Important（应该修）
[架构 / 功能缺失 / 错误处理 / 测试缺口]
#### Minor（锦上添花）
[优化 / 文档]

每条含：file:line + 问题 + 为何重要 + 如何修

### Assessment
Ready to merge: [Yes | No | With fixes]
Reasoning: [1-2 句技术理由]
```

**检视者自查清单：**

- [ ] 聚焦本次 diff，未跑题挑无关老代码
- [ ] 先肯定优点，再分级（Critical/Important/Minor）列问题
- [ ] 每条反馈有 file:line + 原因 + 修法；对事不对人
- [ ] 对照需求/AC 验证功能完整；查逻辑边界与资源泄漏
- [ ] 查信号耦合（无 get_parent 链）、`_process` 性能、类型安全、测试充分性
- [ ] 以三份 specs 规范为基准；格式交 lint；给出明确结论（Yes/No/With fixes）
